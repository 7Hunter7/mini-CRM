# Mini CRM «Объекты и задачи»

Небольшая CRM для строительной компании: руководитель ставит задачи по объектам (стройкам), исполнители выполняют их и отдают на проверку.

Демо: https://new-crm-mini.netlify.app

## Стек технологий

- **Frontend:** React 19, TypeScript, Vite, Tailwind CSS v4, shadcn/ui, TanStack Query, React Router
- **Backend / БД:** Supabase (PostgreSQL, RLS, триггеры, RPC)
- **Деплой:** Vercel (или любой статический хостинг)

## Запуск приложения

1. Установите зависимости:

   ```bash
   npm install
   ```

2. Создайте файл `.env` в корне проекта. Возьмите **Project URL** из Supabase (Project Settings → Data API → Project URL) и **Publishable key** (Project Settings → API Keys → Publishable key).

   > **Важно:** `VITE_SUPABASE_URL` должен быть **без** `/rest/v1/` на конце. Библиотека `supabase-js` добавляет нужные пути автоматически.

   ```env
   VITE_SUPABASE_URL=https://your-project-ref.supabase.co
   VITE_SUPABASE_ANON_KEY=your_publishable_key
   ```

   > Используйте только `anon` ключ. Ключ `service_role` использовать на фронтенде **запрещено** (это нарушает безопасность).

3. Запустите dev-сервер:

   ```bash
   npm run dev
   ```

   Приложение откроется на `http://localhost:5173`.

4. Для production-сборки:
   ```bash
   npm run build
   ```

## Развертывание базы данных

Все SQL-миграции находятся в папке `supabase/migrations/`. Выполните их **по порядку** в SQL Editor вашего Supabase-проекта:

1. `1-profiles.sql` — таблица профилей (связь с `auth.users`)
2. `2-objects.sql` — таблица объектов
3. `3-tasks.sql` — таблица задач
4. `4-task_history.sql` — таблица истории
5. `5-rules.sql` — RLS-политики
6. `6-function.sql` — функция проверки переходов статусов
7. `7-triggers.sql` — триггеры (проверка статуса и логирование)
8. `8-policy.sql` — запрет на изменение/удаление истории

## Безопасность (ключевые решения)

Все правила доступа реализованы **на уровне БД (RLS)**, а не только в интерфейсе. Даже если обратиться к Supabase напрямую (через API), правила останутся в силе.

1. **Исполнитель видит только свои задачи.** RLS-политика на `tasks` разрешает `SELECT` только там, где `assignee_id = auth.uid()`.
2. **Исполнитель видит только связанные объекты.** Политика на `objects` разрешает чтение только тех объектов, где у него есть задачи.
3. **Переходы статусов проверяются в БД.** Триггер `check_status_transition` (BEFORE UPDATE) блокирует недопустимые переходы (например, `new -> review`). Даже прямой `UPDATE` через API вернёт ошибку.
4. **Историю нельзя подделать.** Триггер `log_task_history` (AFTER UPDATE) записывает каждое изменение в `task_history`. RLS-политики на `task_history` разрешают только `SELECT` и `INSERT` (через триггер), а `UPDATE` и `DELETE` запрещены.
5. **Комментарий при возврате на доработку обязателен.** Проверяется на фронтенде (модалка) и сохраняется в `tasks.rework_comment`, откуда триггер копирует его в историю.

## Решения и допущения

- **Статусы в БД** хранятся на английском (`new`, `in_progress`, `review`, `rework`, `done`), а в UI отображаются на русском через словарь `STATUS_LABELS`. Это стандартная практика: латиница в коде, локализация в интерфейсе.
- **Комментарий при возврате на доработку** хранится в отдельной колонке `tasks.rework_comment` (а не через `set_config`), чтобы избежать сложных RPC-вызовов и сохранить простоту.
- **Создание/редактирование объектов и задач** — реализовано базово (через Supabase Table Editor или будущие формы). В текущей версии фокус сделан на цикле жизни задачи и безопасности.
- **Открытая регистрация** отключена в настройках Supabase (Authentication → Providers → Email → Disable signup).

## Что реализовано

- **Роли:** Постановщик (manager) и Исполнитель (executor).
- **Экраны:** Вход, Список объектов, Карточка объекта (с задачами), Карточка задачи (с историей), «Мои задачи» для исполнителя.
- **Цикл статусов:** Новая → В работе → На проверке → Принята / На доработке (с обязательным комментарием). Переходы защищены триггером в БД.
- **История:** Каждое изменение статуса фиксируется в `task_history` (кто, когда, из какого в какой, комментарий).
- **Безопасность:** RLS-политики на всех таблицах, запрет на изменение истории, проверка переходов на уровне БД.
- **UI:** shadcn/ui + Tailwind. Интерфейс показывает только те действия, которые доступны текущей роли в текущем статусе задачи.
